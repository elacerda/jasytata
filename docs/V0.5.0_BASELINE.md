# Jasytata v0.5.0 Gate 0 baseline

## Frozen starting point

The baseline was measured before any v0.5.0 changes, on branch `0.5.0` at
`7613a08b1cd1f23bfc40918c8391cea995085af4`, exactly the published `v0.4.0`
tag target. The working tree had no tracked modifications. Node.js was
`v22.22.3`, npm was `12.0.2`, and the installed Vitest was `2.1.9`.

The starting `make test` run passed **694 tests in 45 files**. Vitest reported
51.67 seconds wall duration; that is a test-run observation, not a performance
acceptance threshold. This is the untouched v0.4.0 baseline; later Gate 0
validation is reported with the branch commit.

Golden comparisons preserve ordered candidates and pointings, stable pointing
identities, coordinates at the existing `1e-10°` contract tolerance where
applicable, coverage outputs, and planner diagnostics. The suite's exact
historical fixtures remain the source of scientific truth; benchmark output is
kept separate from those files.

## Reproducible performance inputs

Run the deterministic programmatic workload set from `frontend/` with:

```sh
npm run benchmark:baseline
```

The harness is `frontend/src/science/gate0-baseline.bench.ts`. It records
workload dimensions, sampling-grid sizes, candidate search/admissible counts,
and selected-plan sizes before timing. Inputs cover small, medium, large,
wide-field, small-footprint/high-resolution, RA-wrap, and high-declination
regions. The lattice stress fixture measures more than two thousand admissible
sites using an explicit pure-enumerator budget; it does not raise the current
1,200-site planner guard. Vitest's `performance.now()`-based benchmark runner
reports operations per second and sample distributions. These timings are
informational and never correctness assertions.

The recorded workload summary is: region-sampling grids of 1,025 (small),
17,227 (medium), 7,442 (large), 5,940 (wide-field), 137,067
(small-footprint/high-resolution), 12,880 (RA wrap), and 11,440
(high-declination) samples. The lattice case searches 4,225 raw sites and
retains 3,721 admissible sites with a benchmark-only limit of 5,000. The
planner-selection case uses the default `splus-t80-south` profile over a
3° × 1.5° region with no existing pointings; Complete and Efficient each
select six pointings.

The harness measures region sampling, candidate enumeration, coverage
intersection, and Complete/Efficient planner selection (which includes the
current candidate ranking path). The current test environment does not provide
a stable real-browser performance target: Aladin rendering is mocked in
automated tests, and React rerender cost varies with browser, hardware, and
viewport. Map rendering and React rerenders therefore remain manual benchmark
categories, with methodology to be fixed before any optimization gate.

## Existing scientific limitations to preserve and report

- The current local projection scales wrapped RA with
  `max(cos(reference DEC), 0.01)` and adds north as a DEC difference. This is
  a local approximation, not an exact spherical projection. Existing high-DEC
  tests establish behavior at their fixtures; they do not prove physical
  accuracy arbitrarily close to a pole. Gate 1 must set an explicit supported
  polar domain and rejection behavior.
- A region plus footprint that crosses the fixed origin's RA branch is refused
  and needs a nearby anchor. RA is not globally flattened into one branch.
- The v0.4.0 legacy S-PLUS path has a documented historical supplemental
  overlap center at high declination. It remains release behavior; the new
  project lattice path must not create arbitrary gap-fill centers.
- Automated map integration exercises Jasytata's boundary-generation path but
  mocks the native Aladin interface. It is not a manual live-browser render or
  rendering-performance measurement.

# Jasytata v0.3.0 implementation roadmap

## Goal

Make Jasytata a telescope- and survey-agnostic pointing and coverage planner while preserving the published v0.2.0 T80-South/S-PLUS behavior as a regression-protected compatibility case.

The v0.3.0 work is developed only on branch `v0.3.0`. The published `main` line remains the stable v0.2.x line while observers are using it.

By the end of v0.3.0, S-PLUS/T80-South must be a bundled reference profile rather than a privileged hard-coded instrument/survey configuration. All S-PLUS/T80-South-specific configuration values must live in a profile file that is valid through the same user-facing profile import mechanism available for arbitrary instruments and surveys.

## Working model

- Planning and architecture decisions: ChatGPT.
- Implementation: Codex, using Luna/Sol or Orion Qwen as appropriate.
- Scientific and regression validation: local execution on `tufao`.
- Implementation proceeds gate by gate. Do not begin the next gate until the current gate passes its acceptance criteria.
- Every gate must preserve the T80/S-PLUS v0.2.0 scientific contract unless an explicitly reviewed compatibility decision says otherwise.

## Scope

v0.3.0 generalizes the existing planner around explicit instrument and survey profiles. It does not become an observing scheduler.

In scope:

- reusable instrument/survey profile schema;
- profile import/export;
- a bundled S-PLUS/T80-South profile file that is loadable through the same mechanism as a user-supplied profile;
- removal of S-PLUS/T80-South-specific configuration values from planner/UI hard-coding once the profile migration is complete;
- per-dataset instrument geometry;
- mixed-instrument coverage;
- generic footprint abstraction;
- footprint position angle;
- rectangular, circular, polygonal and compound/mosaic footprints;
- generic grid/tiling abstraction rather than S-PLUS-specific row assumptions;
- scale-aware inference and coverage tolerances;
- scale-aware numerical coverage sampling;
- generic configurable export contracts;
- regression profiles representing instruments substantially different from T80-South.

Out of scope:

- exposure-time calculation;
- filters and observing sequence optimization;
- airmass, Moon, weather or visibility scheduling;
- mount constraints;
- queue scheduling;
- observatory control;
- automatic optimization of exposure time or cadence.

The internal canonical sky coordinate system remains ICRS for v0.3.0. Other catalogue conventions may be converted at import boundaries in future work, but telescope/survey agnosticism does not require the planner core to carry multiple simultaneous celestial frames.

## Non-negotiable compatibility invariants

1. The bundled S-PLUS/T80-South profile reproduces v0.2.0 behavior for validated regression fixtures.
2. Original catalogue rows and arbitrary metadata remain immutable.
3. Proposals remain reversible and separate until accepted.
4. The application remains fully browser-side and deployable as a static GitHub Pages application.
5. Existing RA=0 wrapping regressions remain valid.
6. Complete and Efficient coverage remain deterministic.
7. The v0.2.0 T80-South reference catalogue continues to load and export successfully.
8. No gate may silently reinterpret existing T80-South catalogue geometry.
9. At release, all S-PLUS/T80-South-specific configuration values must be sourced from an importable profile file using the same schema and loader available to users. Bundling that file as the default preset is a convenience only, not a separate scientific configuration path.

# Gate 1 — Profile schema v2

## Purpose

Replace the current width/height-centric `TilingProfile` with an explicit instrument/survey contract without yet changing planner behavior.

## Proposed model

A profile should separate at least:

- identity and descriptive metadata;
- canonical coordinate assumptions;
- footprint model;
- tiling model;
- inference tolerances/policy;
- coverage numerical policy;
- export policy.

Conceptually:

```text
Profile
├── identity
├── footprint
├── tiling
├── inference
├── coverage
└── export
```

## Footprint schema targets

Support a discriminated union suitable for:

- rectangle;
- circle;
- polygon;
- compound/mosaic.

Each footprint must be expressible in a local tangent-plane coordinate system relative to a pointing center and must support a position angle.

A compound/mosaic footprint is a union of child footprints with local offsets and optional child rotations. This is the generic representation for detector mosaics and gaps.

## Work

- Introduce versioned profile schema, e.g. `schema_version: 2`.
- Convert the bundled S-PLUS/T80-South configuration to the new schema.
- Keep a compatibility adapter where necessary during migration.
- Validation must reject malformed geometry deterministically.
- Profile objects must be serializable JSON.

## Acceptance

- Existing T80 tests still pass unchanged or through an explicitly reviewed adapter.
- Round-trip JSON serialization tests pass.
- Invalid profile fixtures are covered.
- No planner algorithm changes yet.

# Gate 4 — Generic tiling model

## Purpose

Remove the assumption that all automatic plans are rows of constant DEC with a single RA/DEC pitch.

## Work

- Introduce a tiling strategy abstraction.
- Preserve `SPLUS_LEGACY_GRID_V1` as a compatibility strategy, not as planner-core logic.
- Represent generic regular lattices in a local tangent plane using basis vectors or an equivalent geometry that can express:
  - rectangular grids;
  - staggered grids;
  - hexagonal grids.
- Allow a profile to define lattice placement/origin explicitly; avoid duplicating orientation state when basis vectors already encode lattice orientation.
- Treat overlap as a profile/UI convenience for constructing a lattice where appropriate, while the resolved lattice basis remains the authoritative spacing geometry.
- Ensure any S-PLUS/T80-South parameters consumed by the legacy compatibility strategy come from the bundled/importable profile rather than duplicated planner constants wherever the Gate 4 migration reaches those values.
- Define an explicit no-lattice/manual mode for instruments where Jasytata should perform coverage accounting but not infer or generate a regular survey grid.
- Rename generic provenance values such as `region_legacy` to profile-neutral terminology while preserving compatibility in stored regression expectations where required.

## Acceptance

- T80 legacy generation remains unchanged.
- A non-T80 rectangular lattice passes deterministic tests.
- A staggered/hexagonal example passes deterministic tests.
- Planner core no longer contains S-PLUS-specific branching except through the compatibility strategy implementation.

# Gate 6 — Scale-aware coverage engine

## Purpose

Remove numerical constants whose scientific meaning depends on T80's ~1.4 degree footprint.

## Work

- Replace fixed nominal coverage pitch with a scale-aware sampling policy derived from footprint characteristic scale, requested accuracy and computational limits.
- Keep a hard browser-computation cap.
- Make occupied-center tolerance scale-aware or strategy-specific.
- Review gap-fill spacing and candidate limits for small and large FoV instruments.
- Ensure Complete and Efficient semantics remain explicit and deterministic.
- Keep reported sample resolution visible/auditable.

## Acceptance

Regression tests must include at minimum:

- T80-scale footprint (~degree);
- small-field instrument (arcminute-scale);
- substantially larger footprint;
- rotated footprint;
- compound footprint with gaps.

### G9B blocker — polygon intersection false positive

**Status: resolved in G9B1 on 2026-09-28. G9B2 final audit and Gate 9 are PASS.**

G9A direct source review and a runtime diagnostic found a contradiction in the
accepted generic polygon intersection contract. Schema v2 allows a simple
polygon whose local origin lies outside its area. In
the pre-fix `science/footprint-engine.ts::primitiveIntersectsPolygon`, the unconditional
`pointInPolygon(primitive.center, region)` shortcut treats that origin as an
interior footprint point. Consequently, disjoint footprints/regions can return
`true` and count a source as an existing contributor. The shared helper also
filters lattice candidates; sampled containment remains separate. This is not
an exact-intersection guarantee for those valid polygon profiles.

Reproduction uses a validated instrument with `schema_version: 2`,
`id: "g9b-offset-polygon"`, `display_name: "Offset polygon diagnostic"`,
`coordinate_frame: "icrs"` and this footprint/pointing/region:

```typescript
const footprint = {
  type: "polygon",
  vertices_deg: [[1, -0.1], [1.2, -0.1], [1.2, 0.1], [1, 0.1]],
};
const pointing = { ra_deg: 150, dec_deg: 0 };
const region = { vertices: [
  { ra_deg: 149.95, dec_deg: -0.05 },
  { ra_deg: 150.05, dec_deg: -0.05 },
  { ra_deg: 150.05, dec_deg: 0.05 },
  { ra_deg: 149.95, dec_deg: 0.05 },
] };
```

At DEC 0°, footprint east extent is `[1,1.2]°`, while the region extent is
`[-0.05,0.05]°`: they are disjoint. Actual pre-fix shared-function results:
`footprintContainsPoint(footprint, pointing, pointing) === false`; all four
region vertices are outside the footprint;
`footprintIntersectsRegion(footprint, pointing, region) === true` (expected false).
Using `makeCenterProposals([pointing], "manual")`,
`contributingTileCount(region, tiles, footprint) === 1` (expected 0).
The diagnostic used actual modules and common schema validation; no scientific
code or frozen test expectation was changed. All 437 existing tests passed,
so they did not cover this case.

G9B1 first encoded the exact reproduction using the validated instrument and
real geometry/contributor path: the tests failed with `true` and `1` before any
production change. They now return `false` and `0`. The nominal origin remains
a valid shortcut only for rectangles and circles, whose interiors contain it;
arbitrary polygons and polygon children use their actual transformed boundaries.

The boundary classifier tests strict vertex containment, proper edge crossings,
collinear edge overlap with interiors on the same side, and open edge fragments
between vertex contacts. This also repairs aligned/identical polygon overlap and
small-detector edge crossings under the same intersection contract. It retains
the existing `1e-12` geometry tolerance and positive-area semantics: touching
only at an edge or vertex is not a contributor. Rectangular boundaries use the
same exact local-plane classifier; circles retain analytic edge distance.
No coverage density, coordinate convention, PA transform, RA unwrap, lattice
generation, schema validation, or frozen fixture was changed.

The 24 focused regressions in `science/polygon-intersection.test.ts` cover the
original disjoint polygon, true overlap, both containment directions, both
windings, identical/collinear boundaries, inscribed vertices, edge-only crossing
at two scales, touching and near-collinear edges, concavity and bbox-only hits,
nonzero PA, compound detector gaps and composed transforms, rectangle/circle
preservation, real coverage recalculation, candidate filtering and full planning
at RA 150° and RA 0°. Simple concave polygons remain supported by Schema v2.

# Implementation discipline

Each Codex implementation request should target one gate or a small sub-gate only. The implementation prompt should contain:

1. current gate and exact acceptance criteria;
2. files/contracts considered authoritative;
3. explicit instruction to preserve T80 compatibility;
4. tests to add before or alongside implementation;
5. command set to run locally;
6. instruction not to broaden scope into later gates;
7. final report containing changed files, scientific decisions, test results and unresolved risks.

Prefer architectural decisions here in ChatGPT before asking Codex to implement them. Use Luna/Sol for architecture/review when needed and Orion Qwen for implementation-heavy or repetitive work where appropriate.

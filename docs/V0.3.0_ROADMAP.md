# Jasytata v0.3.0 implementation roadmap

## Goal

Make Jasytata a telescope- and survey-agnostic pointing and coverage planner while preserving the published v0.2.0 T80-South/S-PLUS behavior as a regression-protected compatibility case.

The v0.3.0 work is developed only on branch `v0.3.0`. The published `main` line remains the stable v0.2.x line while observers are using it.

## Working model

- Planning and architecture decisions: ChatGPT.
- Implementation: Codex, using Luna/Sol or Orion Qwen as appropriate.
- Scientific and regression validation: local execution on `tufao`.
- Implementation proceeds gate by gate. Do not begin the next gate until the current gate passes its acceptance criteria.
- Every gate must preserve the T80/S-PLUS v0.2.0 scientific contract unless an explicitly reviewed compatibility decision says otherwise.

## Scope

v0.3.0 generalizes the existing planner around explicit instrument and survey profiles. It does not become an observing scheduler.

In scope:

- reusable instrument/survey profile schema;
- profile import/export;
- per-dataset instrument geometry;
- mixed-instrument coverage;
- generic footprint abstraction;
- footprint position angle;
- rectangular, circular, polygonal and compound/mosaic footprints;
- generic grid/tiling abstraction rather than S-PLUS-specific row assumptions;
- scale-aware inference and coverage tolerances;
- scale-aware numerical coverage sampling;
- generic configurable export contracts;
- regression profiles representing instruments substantially different from T80-South.

Out of scope:

- exposure-time calculation;
- filters and observing sequence optimization;
- airmass, Moon, weather or visibility scheduling;
- mount constraints;
- queue scheduling;
- observatory control;
- automatic optimization of exposure time or cadence.

The internal canonical sky coordinate system remains ICRS for v0.3.0. Other catalogue conventions may be converted at import boundaries in future work, but telescope/survey agnosticism does not require the planner core to carry multiple simultaneous celestial frames.

## Non-negotiable compatibility invariants

1. The bundled S-PLUS/T80-South profile reproduces v0.2.0 behavior for validated regression fixtures.
2. Original catalogue rows and arbitrary metadata remain immutable.
3. Proposals remain reversible and separate until accepted.
4. The application remains fully browser-side and deployable as a static GitHub Pages application.
5. Existing RA=0 wrapping regressions remain valid.
6. Complete and Efficient coverage remain deterministic.
7. The v0.2.0 T80-South reference catalogue continues to load and export successfully.
8. No gate may silently reinterpret existing T80-South catalogue geometry.

# Gate 0 — Freeze the v0.2.0 baseline

## Purpose

Create an explicit compatibility boundary before generalizing the scientific model.

## Work

- Record the v0.2.0 release commit/tag used as the compatibility baseline.
- Run the complete current test suite locally on `tufao`.
- Preserve current planner-contract, Efficient coverage and historical golden fixtures.
- Add an explicit T80 compatibility test group if current tests are not clearly separated.
- Record representative T80 planning outputs for:
  - new project with no catalogue;
  - extension of an existing local grid;
  - RA=0 wrapping;
  - Complete coverage;
  - Efficient coverage;
  - manual and imported centers;
  - decimal and sexagesimal export.

## Acceptance

- `make check` passes on `tufao`.
- Compatibility fixtures are clearly identified as v0.2.0/T80 contracts.
- No scientific behavior changes in this gate.

# Gate 1 — Profile schema v2

## Purpose

Replace the current width/height-centric `TilingProfile` with an explicit instrument/survey contract without yet changing planner behavior.

## Proposed model

A profile should separate at least:

- identity and descriptive metadata;
- canonical coordinate assumptions;
- footprint model;
- tiling model;
- inference tolerances/policy;
- coverage numerical policy;
- export policy.

Conceptually:

```text
Profile
├── identity
├── footprint
├── tiling
├── inference
├── coverage
└── export
```

## Footprint schema targets

Support a discriminated union suitable for:

- rectangle;
- circle;
- polygon;
- compound/mosaic.

Each footprint must be expressible in a local tangent-plane coordinate system relative to a pointing center and must support a position angle.

A compound/mosaic footprint is a union of child footprints with local offsets and optional child rotations. This is the generic representation for detector mosaics and gaps.

## Work

- Introduce versioned profile schema, e.g. `schema_version: 2`.
- Convert the bundled S-PLUS/T80-South configuration to the new schema.
- Keep a compatibility adapter where necessary during migration.
- Validation must reject malformed geometry deterministically.
- Profile objects must be serializable JSON.

## Acceptance

- Existing T80 tests still pass unchanged or through an explicitly reviewed adapter.
- Round-trip JSON serialization tests pass.
- Invalid profile fixtures are covered.
- No planner algorithm changes yet.

# Gate 2 — Dataset/profile separation and mixed instruments

## Purpose

Stop assuming that every loaded catalogue uses the active output instrument.

## Work

- Associate each `CatalogueDataset` with a profile/profile reference.
- Keep the active planning/output profile independent from source dataset profiles.
- Existing coverage must use the footprint of each source dataset.
- Existing-grid inference must operate only on compatible datasets selected for lattice inference.
- Other catalogues may contribute coverage without participating in inference.
- Define UI behavior for assigning a profile when loading a catalogue.
- Preserve a convenient default path for the bundled T80 catalogue.

## Acceptance

A regression scenario must work where:

- dataset A uses one footprint;
- dataset B uses a second footprint;
- the new proposal uses a third profile;
- all three contribute correctly to coverage;
- only the intended compatible dataset contributes to lattice inference.

T80-only behavior remains unchanged.

# Gate 3 — Generic footprint engine

## Purpose

Remove rectangle assumptions from display, intersection and coverage.

## Work

Introduce a common footprint API used by every scientific layer, conceptually providing:

- footprint boundary generation;
- point-in-footprint testing;
- polygon/region intersection;
- footprint area;
- local rotation by position angle;
- translation from pointing center to sky coordinates.

Implement and test:

1. rectangle;
2. circle;
3. arbitrary simple polygon;
4. compound/mosaic footprint.

The Aladin renderer, sampled coverage engine and geometric contributor count must consume the same footprint abstraction.

## Acceptance

- Display and scientific masks agree for every supported footprint type.
- Position angle changes the footprint correctly.
- Compound footprints preserve detector gaps.
- Mixed-footprint coverage tests pass.
- T80 rectangular footprint results remain within the frozen compatibility tolerance.

---

# Gate 4 — Generic tiling model

## Purpose

Remove the assumption that all automatic plans are rows of constant DEC with a single RA/DEC pitch.

## Work

- Introduce a tiling strategy abstraction.
- Preserve `SPLUS_LEGACY_GRID_V1` as a compatibility strategy, not as planner-core logic.
- Represent generic regular lattices in a local tangent plane using basis vectors or an equivalent geometry that can express:
  - rectangular grids;
  - staggered grids;
  - hexagonal grids.
- Allow a profile to define a fixed lattice orientation/position angle.
- Define an explicit no-lattice/manual mode for instruments where Jasytata should perform coverage accounting but not infer or generate a regular survey grid.
- Rename generic provenance values such as `region_legacy` to profile-neutral terminology while preserving compatibility in stored regression expectations where required.

## Acceptance

- T80 legacy generation remains unchanged.
- A non-T80 rectangular lattice passes deterministic tests.
- A staggered/hexagonal example passes deterministic tests.
- Planner core no longer contains S-PLUS-specific branching except through the compatibility strategy implementation.

# Gate 5 — Generic existing-grid inference

## Purpose

Make extension of an existing survey scale- and geometry-aware.

## Work

- Move inference parameters out of global T80-calibrated constants.
- Express tolerances primarily relative to expected footprint/lattice scale.
- Infer lattice orientation where the selected tiling strategy allows it.
- Define compatibility tests between dataset profile and active tiling strategy.
- Replace row-specific assumptions where possible with local tangent-plane lattice fitting.
- Keep S-PLUS row-preserving inference available as its compatibility implementation if required for exact historical behavior.

## Acceptance

- Same T80 inference decisions as the frozen baseline.
- Correct recovery of a rotated synthetic lattice.
- Correct rejection of incompatible/unrelated catalogues.
- Tests cover small-FoV and large-FoV regimes so absolute-degree tolerances cannot accidentally dominate behavior.

---

# Gate 6 — Scale-aware coverage engine

## Purpose

Remove numerical constants whose scientific meaning depends on T80's ~1.4 degree footprint.

## Work

- Replace fixed nominal coverage pitch with a scale-aware sampling policy derived from footprint characteristic scale, requested accuracy and computational limits.
- Keep a hard browser-computation cap.
- Make occupied-center tolerance scale-aware or strategy-specific.
- Review gap-fill spacing and candidate limits for small and large FoV instruments.
- Ensure Complete and Efficient semantics remain explicit and deterministic.
- Keep reported sample resolution visible/auditable.

## Acceptance

Regression tests must include at minimum:

- T80-scale footprint (~degree);
- small-field instrument (arcminute-scale);
- substantially larger footprint;
- rotated footprint;
- compound footprint with gaps.

Coverage error against a higher-resolution reference must stay within a documented tolerance for each test case.

---

# Gate 7 — Generic profile and export UX

## Purpose

Make generic capability usable without editing source code.

## Work

- Import profile JSON.
- Export active/custom profile JSON.
- Create/edit profile in the browser for supported geometry and tiling parameters.
- Persist profile only through explicit file export/import; do not introduce a backend.
- Replace T80-specific reset/copy in generic UI with profile-neutral actions while keeping S-PLUS as the bundled default preset.
- Allow catalogue-to-profile assignment.
- Make export policy profile-driven, including at least:
  - RA/DEC column names;
  - decimal or sexagesimal coordinates;
  - optional epoch column;
  - optional position-angle column;
  - additional constant output fields.
- Remove implicit scientific meaning attached to arbitrary source columns such as `PID`; expose optional ID/name/group column mapping instead.

## Acceptance

A user can create a new survey without source code changes by:

1. importing or defining an instrument profile;
2. optionally loading existing catalogues and assigning their profiles;
3. selecting a region;
4. generating/reviewing coverage;
5. exporting centers in the configured survey format.

# Gate 8 — Telescope/survey agnosticism validation matrix

## Purpose

Prove that generic behavior is real rather than an abstraction exercised only by T80-like geometry.

## Required fixtures

At least three deliberately distinct planning profiles:

### A. S-PLUS / T80-South

Compatibility reference.

- ~1.4 degree square footprint;
- legacy survey lattice;
- current catalogue and regression data.

### B. Small circular FoV instrument

Designed to exercise:

- circle footprint;
- much smaller angular scale;
- scale-aware coverage sampling;
- generic lattice or manual mode.

### C. Rotated mosaic instrument

Designed to exercise:

- compound/polygonal footprint;
- detector gaps;
- position angle;
- non-S-PLUS lattice geometry;
- mixed-instrument coverage.

Optional fourth fixture: a wide-field staggered/hexagonal survey.

## Acceptance

For each profile validate:

- new project from zero pointings;
- catalogue loading;
- coverage measurement;
- region planning where supported;
- manual/imported pointings;
- footprint rendering;
- export;
- deterministic repeatability.

`make check` must pass on `tufao`.

## Work

- Rewrite `PRODUCT.md` so S-PLUS/T80-South is the bundled reference profile, not the product definition.

- the full telescope/survey validation matrix passes;

- no backend requirement has been introduced;
- documentation accurately states remaining geometric limits;
- the branch has been reviewed as a complete release candidate.

# Implementation discipline

Each Codex implementation request should target one gate or a small sub-gate only. The implementation prompt should contain:

1. current gate and exact acceptance criteria;
2. files/contracts considered authoritative;
3. explicit instruction to preserve T80 compatibility;
4. tests to add before or alongside implementation;
5. command set to run locally;
6. instruction not to broaden scope into later gates;
7. final report containing changed files, scientific decisions, test results and unresolved risks.

Prefer architectural decisions here in ChatGPT before asking Codex to implement them. Use Luna/Sol for architecture/review when needed and Orion Qwen for implementation-heavy or repetitive work where appropriate.

# Recommended execution order

```text
G0 baseline freeze
  ↓
G1 profile schema v2
  ↓
G2 per-dataset profiles
  ↓
G3 footprint engine
  ↓
G4 tiling abstraction
  ↓
G5 generic lattice inference
  ↓
G6 scale-aware coverage
  ↓
G7 generic profile/export UX
  ↓
G8 validation matrix
  ↓
G9 docs + release candidate
```

Do not parallelize gates that change the same scientific contracts. Within a gate, tests/fixtures and UI-independent science work may be split into separate Codex tasks when their interfaces have already been frozen.

# Jasytata v0.5.0 Gate 3: project lattice validation

## Scope

Gate 3 adds project-owned lattice authoring and a deterministic candidate-site
preview over the selected Gate 2 region. The preview is candidate geometry
only. It does not run Complete/Efficient planning, create proposal pointings,
fill coverage gaps, accept candidates, or export candidate sites. Existing
S-PLUS/T80 planning and registered survey lattices continue through their
existing code paths.

Gate 2 real-browser validation remains pending. Gate 3 real-browser validation
is also pending; the available computer-use inventory reports no browser or
app surface. Automated DOM tests do not establish Aladin's native browser
rendering or wheel behavior.

## Project state and planning mode

The App keeps `ProjectPlanningMode` (`manual_pointings` or `regional_mosaic`),
the last successfully applied `ProjectPlacementPolicy`, and the resolved
candidate preview in project/session state. These values are not added to
`InstrumentProfileV3`, `SurveyProfileV3`, profile registries, or serializers.
Manual pointings use the manual planning mode; no fake manual lattice preset is
created. The initial mode is manual so existing workflows do not switch to a
regional workflow automatically.

The authoring form keeps numeric and coordinate drafts locally. Changing a
draft clears the displayed candidate preview but leaves the last successfully
applied placement policy unchanged. Only a successful explicit **Preview
lattice** applies the policy and resolved candidate set. Invalid basis, origin,
PA, projection, or candidate-budget input leaves that applied policy
unchanged and reports an inline error.

## Authoring modes and units

The compact project-placement controls expose:

- Rectangular grid: east spacing and north spacing.
- Triangular grid: pitch, defined as nearest-neighbor center-to-center spacing.
- Advanced basis: east/north components for vectors 1 and 2.

One explicit `deg`, `arcmin`, or `arcsec` unit selection is converted to
canonical degrees at the authoring boundary. All three modes then use
`resolveProjectPlacement`; React does not construct a second basis algorithm.
The resolved canonical form is the Gate 1 pair of east/north vectors in
degrees. Rectangular zero rotation resolves to `[east spacing, 0]` and
`[0, north spacing]`. Triangular pitch resolves to `[pitch, 0]` and
`[pitch/2, sqrt(3)*pitch/2]`. Advanced vectors use the same frozen basis
validator and tolerance; zero, collinear, near-degenerate, and non-finite
bases are rejected without repair.

## Rotation and physical instrument PA

Lattice rotation has two explicit modes:

- **Independent** stores only the user's lattice angle. It does not derive
  instrument PA.
- **Follow instrument PA** stores the relationship and resolves the effective
  PA from the active instrument/project state at preview time. The angle is not
  copied into a profile or back into the placement policy.

The existing `resolveFootprintForTile` policy resolves the physical camera
footprint and its effective PA. The Gate 1 resolver applies the independent or
follow-PA policy to the basis. Thus the physical footprint PA and lattice
rotation remain separate inputs. If the active policy requires a user PA and
one is unavailable, preview is disabled with a reason. Follow-PA is also
disabled when there is no resolved physical PA to follow. Changing effective
PA invalidates candidate sites because physical footprint intersections may
change, including when lattice rotation is independent.

The placement rotation convention remains the frozen astronomical convention:
zero is north and positive angles are east of north. This placement orientation
is not the selected-region orientation.

## Origin and phase

The user must explicitly select one origin:

- **Region center** uses Gate 1 `latticePlanningOrigin`: midpoint of the
  selected region's continuous unwrapped RA bounds and DEC bounds. It is a
  deterministic bounds midpoint, not a spherical centroid.
- **Fixed sky coordinate** is parsed by the Gate 2 `parseSkyCoordinate`
  function. Decimal RA/DEC degrees and supported sexagesimal forms retain the
  same RA-hours / DEC-degrees semantics. The Gate 1 resolver validates the
  canonical fixed ICRS anchor and projection domain.

There is no automatic phase fitting, selected-tile phase, or grid-to-region
optimization.

## Candidate preview pipeline

The explicit UI action follows this pure pipeline:

```text
project placement draft
  -> ProjectPlacementPolicy
  -> resolveProjectPlacement(policy, selectedRegion, effectivePA)
  -> canonical GenericLatticeTiling basis and origin
  -> generateLatticeCandidates(selectedRegion, tiling, resolvedFootprint, 1200)
  -> full deterministic LatticeCandidate set
```

`previewProjectLattice` composes the Gate 1 resolver and existing candidate
generator. The existing generator enforces the finite coefficient-range
budget before enumeration, enumerates ascending `j` then ascending `i`, and
retains only centers whose resolved physical footprint has positive-area
intersection with the selected polygon. A zero-admissible result is reported
as a placement diagnostic. No candidate center is shifted and no gap-fill
center is synthesized.

The preview state retains each candidate's stable `(i,j)` identity and sky
center. It contains no `TileRecord`, proposal ID, generation method, acceptance
state, or export row. The map receives only center coordinates through a
dedicated `projectCandidateCenters` property. It uses the existing **Candidate
lattice** overlay and visual toggle; hiding/showing the overlay does not alter
the preview, placement, candidate count, proposal state, coverage, or exports.
The map culls off-screen sites and limits overlay rendering to 1,200 sites,
while the complete generated set remains in project preview state. The
candidate budget itself is 1,200 for this gate.

The compact summary reports the user-defined preset, canonical basis, resolved
rotation and follow-PA relationship, explicit origin and resolved coordinate,
and the count as **candidate sites · preview only**. Nominal-envelope geometry
is called approximate in the controls and candidate-intersection summary.

## Capability rules

Capability derivation uses footprint semantics, not profile IDs:

- `observed_area`: may author and preview project placement when a region and
  required PA are resolved.
- `nominal_envelope`: may author and preview with explicit approximate or
  envelope wording.
- `target_access`: cannot enter regional project-lattice mode; no area-coverage
  claim is made.
- Legacy profiles without explicit v3 footprint semantics do not gain this
  project preview capability. Existing legacy survey planning remains
  unchanged.

Preview further requires `regional_mosaic` mode, a selected region, and any
required resolved instrument PA. Capability diagnostics identify whichever
requirement is missing. Existing region-authoring controls are available for
semantically supported standalone instruments so a project preview can receive
a region; this capability does not enable plan generation. Target-access
profiles do not receive that regional selection action.

## Dependency invalidation and reset

Independent project placement is preserved when only the region, active
instrument, or effective PA changes. Resolved candidates are cleared and
must be previewed again after a selected-region change, instrument geometry or
instrument identity change, effective PA change, or edit to lattice draft
inputs. A strategy switch on the same instrument does not by itself invalidate
candidate geometry. Failed preview validation never replaces the stored
placement policy or creates plan state.

Layer visibility remains visual-only. New project clears the project planning
mode, applied placement, lattice preview, region, and other existing
project/session state while retaining the registered profile library and theme
under the existing reset contract.

## Known scientific and UI limitations

The preview inherits Gate 1's local east/north approximation:

```text
east = wrapped ΔRA * max(cos(reference DEC), 0.01)
north = ΔDEC
```

This is not a spherical or gnomonic projection. High-declination behavior is
limited by the frozen cosine floor, exact poles are outside the supported local
domain, and regions or footprint-expanded ranges that cross the fixed anchor's
RA branch are refused. Approximate nominal envelopes remain approximate.
Candidate intersections are geometry evidence only; this gate provides no
Complete/Efficient coverage guarantee, gap/overlap claim, observing-sequence
expansion, generic regional plan, or project import/export.

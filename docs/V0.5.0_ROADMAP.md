# Jasytata v0.5.0 roadmap

## Authority and release baseline

This document is the development and acceptance authority for v0.5.0. Work is
on branch `0.5.0`, based on the published v0.4.0 release at commit
`7613a08b1cd1f23bfc40918c8391cea995085af4` and tag `v0.4.0`. The v0.4.0
scientific behavior remains frozen and regression-protected, including the
intended T80-South/S-PLUS compatibility contract and its inherited v0.2.0
behavior. Do not amend its history, move its tag, or change `main` as part of
this work.

The central v0.5 project state remains:

```text
instrument geometry
  + resolved instrument PA
  + user-declared project placement policy
  + selected sky region
  -> canonical lattice candidate geometry
  -> candidate-only preview at Gate 3
  -> existing deterministic Complete/Efficient selection at Gate 4
```

Gate 3 preview sites are not proposed pointings, a regional plan, or a
Complete/Efficient result. Gate 4 explicitly connects canonical project
candidates to the existing regional planner; preview remains optional and is never scientific authority.

Project placement belongs to the user's project. It is not part of an
instrument profile and does not claim to be an official survey or observing
strategy. Instrument geometry, observing sequence, placement, and sky region
remain separate inputs.

The current implementation scope is Gate 6 only: measured performance and
responsiveness improvements with Gates 0–5 scientific behavior frozen. Gates
0–5 are committed on branch `0.5.0`; the pre-optimization checkpoint is
`8512ac9bebf1eca7f84fcaeaf59cdc7b5e9ae5db`. Candidate enumeration/order,
Complete/Efficient stopping, coverage mathematics, nominal project identity,
sequence expansion/provenance and S-PLUS remain regression-protected.
Project workflow, manifest import/export and persistence belong to Gate 7 and
must not be implemented as performance work. Gate 6 may use a local Worker
only after measured synchronous optimization justifies it. Real-browser checks
for Gates 2–6 remain release acceptance work for Gate 8. See the individual
gate validation records for evidence and limits.

## Gate 0 — frozen baseline

Before production scientific behavior changes:

- Preserve the v0.4.0 release commit and run the complete regression suite from
  that starting point.
- Reuse current planner-contract, golden, coverage, lattice, profile, and
  S-PLUS/T80 fixtures wherever possible. Add a correctness fixture only when
  an acceptance case is genuinely absent.
- Preserve candidate ordering, pointing identities, coordinates within the
  current documented tolerance, coverage outputs, and planner diagnostics.
- Establish deterministic inputs for small, medium, large, and wide-field
  regions; a small footprint at high resolution; thousands of lattice sites;
  RA wrap across 0/360 degrees; and high-declination edges.
- Measure region sampling, candidate enumeration, coverage intersection,
  candidate ranking/planner selection, map rendering, and React rerenders.
  Measurements are informational and have no wall-clock pass/fail threshold.
- Record fixture inputs separately from golden scientific outputs. Map-render
  and React rerender timings may remain manual if the test harness cannot
  measure real-browser work consistently.
- Establish measurements only. Do not tune algorithms, change budgets, or
  optimize based on Gate 0 timings.

The v0.4.0 lattice implementation's existing rules are part of the baseline:
normalized basis determinant magnitude must exceed `1e-12`; range bounds expand
the footprint bounds and add one integer coefficient at each end; candidates
are enumerated by ascending `j`, then ascending `i`; and a search over more
than 1,200 lattice sites is refused by the current planner. RA uses a
continuous local branch about the projection origin and regions or expanded
footprints that cross that branch are rejected. Keep these compatibility rules
unchanged in Gate 0. A later gate must explicitly justify any changed budget
and keep the size guard before enumeration. The stress benchmark's larger
explicit budget measures the pure enumerator only; it does not change planner
policy.

The existing v0.4.0 legacy S-PLUS planner retains its historical behavior,
including a documented high-declination supplemental overlap center. That
release path is regression-protected. The new project planner must follow the
candidate admissibility contract below and must not inherit arbitrary
gap-filling behavior.

## Gate 1 — contracts to freeze before implementation

### Independent orientation inputs

Keep these concepts independent:

- instrument position angle (PA), which orients the footprint on the sky;
- lattice rotation, which is expressed by the placement basis vectors;
- region orientation, which orients a selected region rectangle or other
  region shape.

None implies either of the others. A future project authoring choice may offer
`Lattice rotation: Independent | Follow instrument PA`, but `Follow instrument
PA` must be explicit project state. The planner consumes resolved basis
vectors and resolved footprint orientation independently.

### Local east/north and ICRS geometry

Write and validate a formal local east/north ↔ ICRS contract before the
regional planner is implemented. It must specify:

- the projection/reference origin and the relationship between a resolved
  local offset and its ICRS coordinate;
- normalization and unwrapping of RA across 0/360 degrees;
- behavior and tested validity limits at high declination and near either
  pole;
- true local east/north angular offsets, distinguished from raw RA
  differences;
- whether rectangle edges touching have zero intersection area, and how
  positive-area intersection is decided numerically;
- explicit rejection of regions or footprint-expanded search domains outside
  the supported projection branch.

Preserve the v0.4.0 numerical projection in this release. It scales wrapped RA
difference by the reference declination's clamped cosine and uses DEC
difference for north; it is a local approximation, not a spherical rectangle
projection. A numerical projection change requires separate scientific
references, edge-case tests, and independent acceptance. Gate 1 must identify
the supported polar limit and its refusal behavior; do not silently extend the
domain by clamping or wrapping an unsupported region.

### Basis and lattice validation

Require finite basis components, non-zero vectors, non-collinear/non-degenerate
vectors, positive rectangular spacings, and a positive triangular pitch. A
rectangular lattice has two positive-length orthogonal vectors; its orientation
is carried by those vectors. Use one explicit normalized determinant tolerance
in both basis validation and candidate generation. Preserve the current
`1e-12` threshold unless a separate validated decision changes it.

Define triangular `pitch` as the nearest-neighbor center-to-center distance.
For basis vectors `b1` and `b2`, require both norms to equal `pitch`, their
included angle to be 60° or 120° (handedness may differ), and
`abs(det(b1, b2)) = sqrt(3) * pitch^2 / 2`, within a documented numeric
tolerance. The canonical unrotated basis is
`b1 = (pitch, 0)`, `b2 = (pitch / 2, sqrt(3) * pitch / 2)`.

An ICRS fixed origin must have finite coordinates, RA in `[0, 360)` degrees,
and DEC in `[-90, 90]` degrees; it must also lie inside the projection domain
frozen by Gate 1. Do not treat an ICRS-valid pole as automatically valid for a
local projection.

### Origin, phase, and candidate admissibility

Freeze the two placement origins:

- `region_center`: midpoint of the region's continuous unwrapped RA bounds and
  DEC bounds, matching the deterministic v0.4.0 lattice planner. This is a
  bounds center, not a spherical centroid. A centroid is allowed only as a
  separately specified and validated alternative.
- `fixed_anchor`: the declared valid ICRS coordinate is lattice site `(0, 0)`.

There is no automatic phase fitting in v0.5.0. Before Gate 4, freeze candidate
admissibility as follows:

1. Derive a finite integer search range from the selected region, the resolved
   basis, the footprint bounds, and the declared origin/phase.
2. Check the finite search range against an explicit candidate budget before
   enumeration.
3. Enumerate in canonical ascending `j`, then ascending `i` order.
4. Retain only sites whose footprint has positive-area intersection with the
   region. Edge contact alone is not positive area.
5. Keep lattice centers at their declared coordinates. Never perturb centers
   or generate arbitrary gap-fill centers.

Document the normalized determinant tolerance, footprint-bound expansion and
finite integer margin, RA-branch limit/refusal behavior, and candidate budget
in the planner contract and its tests. The Gate 0 values above describe the
v0.4.0 baseline; Gate 1 must make any v0.5-specific budget explicit before
Gate 4 implementation.

The existing v0.4.0 RA branch uses a half-width of
`180° * max(cos(reference DEC), 0.01)` in local east. It refuses a region or
footprint-expanded range that reaches or exceeds that branch and excludes
remote padded candidates rather than wrapping them into duplicate sky sites.

### State invalidation

Do not clear all project context when one input changes. Independent user input
survives unrelated changes. At minimum, model these dependencies:

```text
region
  -> region-centered placement origin
  -> candidates
  -> plan/coverage

instrument geometry / PA
  -> footprint
  -> candidate admissibility
  -> coverage

project placement
  -> lattice
  -> candidates
  -> plan/coverage

observing strategy
  -> exposure sequence
  -> expanded plan/export
```

Changing instrument or strategy must not erase an independently defined sky
region. Invalidate derived state that depends on a changed input; retain
unrelated region, placement, and user-entered values.

### Pure planner boundary

Do not add a Web Worker in Gate 0. Keep the future scientific planning core
pure with respect to UI state, independent of React, DOM, and Aladin,
serializable in and out, deterministic, and independent of future chunk size.
Moving that core into a Worker later must not change its scientific results.

### Reproducibility manifest

IndexedDB persistence remains deferred. v0.5.0 should eventually export and
import a project-level manifest such as `jasytata-project.json`, separate from
pointing CSV. It must preserve enough canonical state to reconstruct the
planning problem, including Jasytata/planner version; instrument reference;
observing-strategy reference when present; `user_declared` placement
provenance; basis; origin; selected region; PA inputs; Complete/Efficient
policy; and all scientifically relevant planner parameters. Do not implement
the manifest in Gate 0.

## Validation and working discipline

Use `AGENTS.md` and code-review-graph: minimal context first, graph navigation
before source reads, impact analysis for existing-code changes, and change
review before final validation. The graph is navigation only; source, tests,
and scientific contracts are authoritative.

Gate 0 validation is:

```sh
make test
make lint
make typecheck
make build
git diff --check
```

GitHub Pages deployment remains restricted to `main`. Development-branch and
pull-request CI must run tests, lint, typecheck, and build without invoking a
deployment workflow. Never modify, move, recreate, stage, or delete local
untracked `.codex/` or `poly.txt`.

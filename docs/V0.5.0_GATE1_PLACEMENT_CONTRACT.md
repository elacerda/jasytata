# Jasytata v0.5.0 Gate 1: project placement contract

## Scope and data ownership

Project placement is user-owned project/runtime state. The TypeScript model
uses `ProjectPlacementPolicy`, with distinct manual and lattice variants.
Lattice input carries `provenance: "user_declared"`; resolution preserves that
provenance in `ResolvedProjectPlacement`. The project-specific discriminators
keep these values separate from `GenericLatticeTiling`, instrument profiles,
and observing-strategy profiles.

The canonical mathematical lattice remains the existing two-vector form:

```ts
basis_deg: [[east1_deg, north1_deg], [east2_deg, north2_deg]]
origin:
  | { type: "region_center" }
  | { type: "fixed_anchor"; ra_deg: number; dec_deg: number }
```

`resolveProjectPlacement` returns the declared origin policy, canonical
`basis_deg`, and `resolved_origin` ICRS coordinates. The resolver is pure,
validates the selected region and project inputs, and does not enumerate
candidates, calculate coverage, mutate a profile, or access React, DOM, or
Aladin. Inputs and outputs contain only JSON/structured-clone-safe records,
arrays, strings, and finite numbers. No project state is serialized into a
profile, and this gate adds no Schema v4.

The project persistence boundary remains future work: a future
`jasytata-project.json` stores project placement separately from instrument
profile and observing-strategy library data. Gate 1 adds no import/export or
browser storage.

## Independent orientations

These are separate inputs and must not imply one another:

- Instrument PA orients the physical instrument footprint.
- Lattice rotation orients the project placement basis.
- Region orientation belongs to the selected region geometry.

Project lattice authoring has `rotation.mode: "independent"` with an explicit
angle, or `rotation.mode: "follow_instrument_pa"`. Follow mode requires a
resolved instrument/project PA and resolves that angle before candidate
generation. The resulting lattice contains ordinary basis vectors and needs
no follow-PA branch in the candidate engine. Independent mode ignores any
instrument PA passed to the resolver. Lattice rotation is not stored in an
instrument profile, and instrument PA is never inferred from lattice rotation.

## Presets and rotation convention

All authoring modes produce the same canonical two-vector basis. Angles are in
degrees. Both basis vectors use `rotateLocalOffset`, the existing Jasytata
astronomical PA convention:

```text
(east, north) ->
(east*cos(theta) + north*sin(theta), north*cos(theta) - east*sin(theta))
```

Zero is north; positive angles are east of north, so positive rotation moves a
north vector toward east. For a rectangular east vector, a positive 90-degree
rotation maps east toward south. This is the same convention as physical
footprint PA, applied independently to the lattice vectors.

### Rectangular

East and north spacing must each be finite and positive. Before rotation:

```text
b1 = [east_spacing_deg, 0]
b2 = [0, north_spacing_deg]
```

### Triangular

`pitch_deg` is the nearest-neighbor center-to-center spacing. Before rotation,
the equilateral basis is:

```text
b1 = [pitch_deg, 0]
b2 = [pitch_deg / 2, sqrt(3) * pitch_deg / 2]
```

Both vectors and their difference have norm `pitch_deg`; rotation rigidly
rotates both vectors without changing those spacings.

### Advanced basis

Advanced authoring accepts the canonical two vectors directly. The supplied
vectors are the zero-rotation basis; the same explicit independent/follow-PA
rotation policy may rotate both. It permits oblique non-collinear lattices and
does not infer which preset a basis may resemble.

## Basis and anchor validation

`validateLatticeBasis` is shared by project resolution, generic candidate
range calculation, and Schema v2 profile validation (Schema v3 delegates to
that v2 lattice validator). This preserves the existing profile acceptance
rule while preventing the project and candidate paths from drifting.

For vectors `b1` and `b2`, the validator requires exactly two finite east/north
components per vector, finite non-zero vector norms, and:

```text
abs(det(b1 / norm(b1), b2 / norm(b2))) > 1e-12
```

The `1e-12` dimensionless normalized-determinant cutoff is the frozen Schema v2
and candidate-generation threshold. Normalizing each vector before the
determinant test makes the degeneracy decision independent of angular scale.
Preset spacing/pitch must be finite and positive. Fixed-anchor RA must be in
`[0, 360)` degrees. DEC must be strictly inside `(-90, 90)` for the local
projection; the exact ICRS poles are valid coordinates but unsupported local
projection anchors.

## Origin and phase

`fixed_anchor` is the ICRS location of lattice coefficient `(i, j) = (0, 0)`.
`region_center` has no fitted phase: it resolves to the midpoint of the
selected polygon's canonical unwrapped RA bounds and its DEC min/max bounds:

```text
RA  = modulo(ra_start_deg + ra_span_deg / 2, 360)
DEC = (dec_min_deg + dec_max_deg) / 2
```

This is the deterministic bounds center used by the existing lattice planner,
not a spherical centroid. Equivalent vertex traversals produce the same center
within floating-point rounding. There is no centroid fitting, automatic phase
optimization, or “fit grid to region”.

## Frozen local sky transform and supported branch

The current v0.4 local approximation remains unchanged. For reference
`(ra0, dec0)` and sky coordinate `(ra, dec)`, in degrees:

```text
east  = wrapped_delta_ra(ra, ra0) * max(cos(dec0), 0.01)
north = dec - dec0
```

`wrapped_delta_ra` is the shortest signed RA branch in `[-180, 180)`. Forward
conversion is:

```text
RA  = modulo(ra0 + east / max(cos(dec0), 0.01), 360)
DEC = dec0 + north
```

RA outputs are canonicalized to `[0, 360)`. East/north are local angular
offsets, not raw RA/DEC differences. The `0.01` cosine clamp near either pole
is an approximation and a recorded limitation. This is not a full spherical
or gnomonic polygon projection and is not claimed to be exact spherical
geometry.

Selected polygons are validated to have finite canonical ICRS vertices,
declinations away from the exact poles, and RA span no greater than 180
degrees. Candidate planning refuses a region or footprint-expanded range that
reaches the fixed anchor's local RA branch boundary. The existing engine also
excludes remote padded lattice sites outside that branch rather than wrapping
them into duplicate centers, and skips centers at or beyond a celestial pole.
Near-pole clamp behavior remains as-is; the tests record it rather than
changing it.

## Candidate admissibility and determinism

The existing `generateLatticeCandidates` remains the only lattice enumerator:

```text
selected region
+ resolved basis
+ explicit origin/phase
+ resolved physical footprint
        -> finite coefficient range
        -> canonical enumeration
        -> positive-area footprint/region intersection
        -> admissible candidates
```

The coefficient range conservatively expands by the footprint's local bounds
and one integer at each end. The explicit candidate budget is checked before
enumeration (the existing planner policy remains 1,200 sites). Enumeration is
ascending `j`, then ascending `i`. A candidate is retained only when the
physical footprint has positive-area intersection with the selected region;
boundary-only contact is excluded. Footprint PA and lattice rotation remain
independent. Candidate centers are never moved, phase is never perturbed, and
no off-lattice or gap-fill centers are synthesized.

## Dependency, persistence, and Worker boundary

The dependency model for future application state is:

```text
region
  -> region-centered placement origin
  -> candidates
  -> plan/coverage

instrument geometry / instrument PA
  -> resolved footprint
  -> admissibility/coverage

project placement
  -> resolved lattice
  -> candidates
  -> plan/coverage

observing strategy
  -> observing sequence
  -> expanded plan/export
```

Changing instrument or observing strategy does not inherently invalidate the
independently selected sky region. Future state should invalidate derived
dependent values and retain unrelated user inputs. Gate 1 does not refactor
App state or implement UI invalidation machinery.

The project-placement resolver is a pure serializable boundary for later
planning work. It has no browser or framework dependencies, so candidate
planning can later move behind a Web Worker boundary without changing this
contract or the science. Gate 1 adds no Worker.

observations only and have no Gate 1 pass/fail threshold.

# Jasytata v0.5.0 Gate 4: generic regional planning validation

## Scope and architecture

Gate 4 connects user-declared project placement to the existing regional planner
on branch `0.5.0`, starting at Gate 3 commit
`1c34023e1b54d0d27c3c03a93d881700c34ef12c`. No observing-sequence expansion,
project JSON import/export, Workers, optimization, scheduler, fibre allocation,
or off-lattice gap filling is introduced. Instrument/profile documents, the
Inter font, historical scientific goldens, `main`, and `v0.4.0` are unchanged.

```text
registered survey -> existing registered inference/fallback/candidates --+
                                                                       |
project inputs -> resolveProjectPlacement -> generateLatticeCandidates -+
                                                                       v
                                                   existing greedyChoose
                                                       Complete/Efficient
                                                                       v
                                                  existing proposal review
                                                   accept/cancel/remove
```

`planRegion` retains its existing arguments and accepts one optional final
`ProjectLatticeCandidateSource`: real instrument ID, canonical project policy,
physical PA input, and optional real observing-strategy association. It accepts
no map visibility, viewport, reference marker, React state, or cached preview.
Project resolution uses exactly the Gate 1 resolver and existing Gate 3 lattice
enumerator. It reconstructs candidates on every Generate action. Preview is
optional and remains an independent display of all admissible sites.

`CanonicalLatticeSource` is the internal boundary for registered and project
lattices. `selectLatticeSource` shares coverage-grid construction, useful masks,
selection, metrics and proposal assembly. Registered inference, occupancy and
legacy supplemental-overlap generation retain their original paths. There is
one `greedyChoose` definition and one ranking loop, gain safeguard and Efficient
stopping implementation in `coverage.ts`; both sources call it. No second
Complete/Efficient planner exists. The legacy path's existing two selection
passes still use that same function.

`ProjectCoverageProfile` adapts the real instrument to existing coverage
interfaces. It is a runtime geometry bridge, not a registered survey or profile
document. An explicit `project_instrument_id` selects real instrument geometry
and semantics. Project bridges bypass survey lookup even if instrument and
survey IDs collide. Profile serializers/registries are not extended.

## Selection and coverage contracts

Complete still targets all weighted selected-region samples, stopping at
sampled completion, exhaustion of useful admissible sites, or the existing
`1e-10` fractional minimum-gain safeguard. Centers are never shifted, phase is
never fitted, and missing coverage never creates additional project centers.
The optional project-only `selection_stop` reports `coverage_complete`,
`candidate_lattice_exhausted`, `gain_safeguard`, or `marginal_efficiency`.
Registered response shape and diagnostics remain frozen. A valid zero-site
placement returns zero proposals, sampled metrics and an explicit diagnostic;
Accept is disabled. Exhaustion with holes explains that the declared placement
cannot fully cover the sampled region. No spacing/phase repair is offered.

Efficient uses the same marginal gain, physical footprint area, strict threshold
comparison and deterministic tie ordering. The project adapter reuses the
existing policy (`min_coverage = 0.995`, `min_marginal_efficiency = 0.03`) from the
frozen policy definition; it is a runtime project choice, not instrument or
observing-strategy provenance. No instrument-ID threshold dispatch is added.
Exact tests exercise the strict 0.03 comparison, coverage floor, gain safeguard
and inherited final-index tie preference.

Coverage sampling, containment, projection, mixed-scale selection, numerical
error bounds and under-resolution refusal are unchanged. Project runs use the
existing v3 generic density of eight samples per smallest contributing footprint
axis and the existing fallback sample budget of 90,000. Compatible enabled
catalogue/accepted rows contribute coverage through the existing basis filter
and masks; unrelated roles do not. Catalogue rows never rewrite project basis,
rotation, origin or phase. Project output is nominal single-exposure geometry;
a real strategy association does not expand an observing sequence.

- `observed_area`: supports Complete/Efficient using the declared observed-area
  geometry and existing sampling/error model.
- `nominal_envelope`: supports planning but metrics, readouts, notices and
  diagnostics explicitly retain approximate/envelope wording, including a
  zero-proposal result. No authoritative physical observed-area claim is made.
- `target_access`: both the capability layer and scientific planner refuse
  regional area planning. No fibre or target completeness is claimed.

## Identity, PA, provenance and export

Candidate enumeration remains ascending `j`, then `i`. Each useful project mask
carries its exact `latticeSite`; greedy selection retains it, and proposal
assembly looks up the exact site rather than treating proposal order as science.
Generated records retain `metadata.lattice_i/j` and:

```ts
placement_provenance: {
  origin: "user_declared",
  project_lattice: { i, j, placement: resolvedProjectPlacement }
}
```

The resolved placement includes canonical degree basis, explicit origin,
resolved ICRS anchor and rotation policy. Session proposal IDs can change upon
acceptance without changing lattice identity or placement provenance. Pointings
identify the real instrument; `output_strategy_id` is null for standalone
instruments and references only a selected real strategy otherwise.
`declared_profile_lattice` is never assigned to project placement.

Physical PA is resolved by the existing footprint resolver. Per-pointing PA and
user-selected PA are snapped to proposal records under their existing policies;
fixed PA remains declared by the real instrument profile. Independent lattice
rotation does not change PA. Follow-PA resolves the project basis first, while
the footprint retains its independently resolved physical PA. Tests compare
selected centers to `i*b1 + j*b2` in the frozen local frame within `1e-10°`.

The existing instrument coordinate CSV can export accepted project centers with
`PLACEMENT_ORIGIN=user_declared` and physical PA. Candidate sites stay outside
proposal/export rows. Lattice provenance is runtime state; adding CSV fields or
project manifests is deferred. Real-strategy exports retain their existing
policy, with project rows remaining nominal instead of expanding sequences.

## UI and state dependencies

Regional mosaic reuses Coverage strategy and Generate plan. Apply placement
validates/saves the declaration without enumerating a preview. Preview lattice
validates/saves and displays all admissible sites. Generate plan reconstructs
its own candidate source and selects a coverage subset. Draft edits invalidate
science and disable generation until valid placement is applied again. Invalid
submissions preserve the previous applied policy.

Capabilities separately report authoring, preview and project-plan generation.
Generation requires regional mode, selected region, resolved valid placement,
required physical PA and the other existing planner prerequisites, including
resolved dataset instrument assignments. Preview count or visibility is never
a prerequisite. Instrument geometry and user-defined project placement have
separate labels; no MUSE/KCWI survey is invented.

Region, placement/draft, effective PA, instrument/context and coverage-strategy
changes invalidate pending project proposals, plan diagnostics and derived
metrics. Delayed plan/measurement results cannot restore stale state. Accepted
pointings remain user data and retain their original site/PA/provenance; current
coverage can be recomputed for valid current context. Switching to Manual
clears/hides regional derived state while preserving independent region and
placement inputs. Candidate-layer visibility and reference-marker edits leave
scientific inputs and results unchanged.

## Browser validation and known limitations

The real computer-use inventory on 2026-10-01 returned no apps or browsers.
No manual-browser success is claimed. Gate 2 native wheel/touchpad/Aladin checks,
Gate 3 lattice map/rendering checks, and Gate 4 live author/apply/preview/generate,
proposal review, stale-state and narrow-screen checks remain pending for Gate 8.
DOM integration tests validate application boundaries, not live Aladin behavior.

Inherited scientific limits remain: wrapped local RA/cos(DEC) approximation,
`0.01` cosine floor, excluded exact poles and unsupported RA branch, normalized
basis determinant cutoff `1e-12`, 1,200 search-site budget checked before
enumeration, and finite sampling budget/under-resolution refusal. The existing
region validator also rejects plane area below `1e-5` square degrees; very small
IFU-sized regions can therefore be refused even when the footprint is valid.
No projection, minimum-area, sampling or error-bound method is changed here.
Sampled completion does not certify physical gap-free or spherical coverage.
Sparse project lattices can leave holes; nominal envelopes remain approximate.

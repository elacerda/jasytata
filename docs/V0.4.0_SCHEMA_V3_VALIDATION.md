# Jasytata v0.4.0 Schema v3 validation — Gate 6A

## Purpose and gate boundary

Schema v3 is the persistent format for the v0.4 scientific semantics that the
strict v2 format cannot express. It also represents an instrument-only profile
without manufacturing a survey. Release version 0.4.0 alone does not cause a
document to become v3. A complete instrument/survey pair with no v3 semantics
can remain v2.

Schema v2 remains a first-class legacy format. Its meaning is unchanged: a v2
document has the required instrument/survey pair, and a v0.4 reader must not
infer v3 fidelity, footprint role, provenance, PA policy, sequence, or placement
authority from it. The corrected T80-South/S-PLUS v2 profile, registered
`legacy_splus`, inline-v1 compatibility behavior, existing imports, lattice and
footprint behavior, and Gate 5 runtime behavior remain protected.

Gate 6A covers persistent representation, strict validation, registry/document
lifecycle, and v2 reading. Gate 6B owns role-aware coverage behavior and
mixed-scale sampling correctness. Gate 6C owns completion and final validation
of the selected real-instrument profile library. Gate 7 owns UI and profile
authoring workflows. This document records the Gate 6A contract and its
implementation acceptance evidence; Gate 6 remains in progress.

## Document shapes and version dispatch

V2 documents continue to contain exactly `instrument` and `survey`, both with
`schema_version: 2`. Existing v2 structural and scientific validation applies
without v3 fields or defaults.

A v3 file contains exactly one of these supported shapes:

1. One v3 `instrument` profile.
2. One v3 `survey` strategy whose instrument reference is resolved against the
   registry during registration.
3. A matching v3 `instrument` and v3 `survey` pair, validated and registered
   atomically.

A v3 document with neither member, mismatched pair IDs, or a mixed v2/v3 pair
is invalid. At registration, a survey-only document must reference a registered
v2 or v3 instrument; a v2 instrument keeps legacy semantics and is not eligible for
role-aware metrics until explicitly classified by a v3 instrument profile.
V3 instrument-only profiles support registry lookup and the existing source
assignment, rendering, manual/imported center, and generic ICRS coordinate paths
where those runtime paths already accept an instrument. Without a selected
survey, survey-specific tiling, lattice inference, overlap policy, completion
percentages, and named survey constants are unavailable. The session's manual
output context is not a synthetic survey profile.

Dispatch uses the declared schema version. V2 documents are validated under v2
rules, including rejection of v3-only fields. V3 documents are validated under
v3 rules and are never silently downgraded. Unsupported or missing versions fail
clearly; the reader does not guess a version or mutate the input during
validation. Unknown keys in versioned scientific objects fail unless the
contract explicitly defines a free-form map. V2's declared
`export.constant_fields` map remains its existing intentional free-form
exception; it is not a general extension mechanism.

## V3 persistent concepts

### Provenance

Each v3 profile has nonempty canonical primary references. A reference is a URL
or DOI with optional title and section/locator. Parameter-level sources cover
physical footprint dimensions or vertices and persisted strategy geometry,
including sequence offsets and lattice basis/origin values. Derived parameters
record how they were derived. URLs are stored in canonical URL form, DOIs are
normalized to lowercase, references are sorted by canonical locator, and
parameter sources are sorted by path. Meaningful exposure order remains
untouched. Assumptions and known limitations are durable string lists. These
fields provide scientific provenance; they are not a bibliography manager.

### Fidelity and approximation notice

The only fidelity values are `exact` and `approximate`. Fidelity is interpreted
for the declared instrument mode and footprint role. `exact` means the modeled
boundary is supported at the stated mode and precision for that role. For
`observed_area`, that is the modeled one-exposure science-active area; it makes
no promise about depth, throughput, calibration, target completeness, or exact
spherical area. For `nominal_envelope` or `target_access`, exactness describes
only the cited envelope and does not make it observed area.

`approximate` records an explicit geometric simplification. An approximate
observed-area result must be labeled approximate. An envelope/access result is
an envelope diagnostic, never observed science area. Approximate geometry and
all envelope/access geometry require a nonempty `approximation_notice` that
states what the representation stands for and what it does not. Assumptions and
limitations remain explicit durable metadata.

### Footprint role

The v3 role is explicit as `footprint_semantics.role` and is one of:

- `observed_area`: modeled science-active area for one exposure, exact or
  explicitly approximate.
- `nominal_envelope`: nominal optical, IFU, or bundle outline used for planning;
  it can include gaps, unilluminated edges, or unmodeled fibre holes.
- `target_access`: nominal field or patrol envelope in which targets may be
  considered for access; it does not represent fibre assignment.

Gate 6A persists, validates, and exposes the role. It does not change coverage
metrics. V2 profiles are not assigned a role during deserialization; in
particular, a target-access footprint cannot gain an implicit `observed_area`
role. Gate 6B owns the behavior that excludes envelopes and target-access
geometry from observed-area calculations.

### Stable instrument/mode identity

Stable profile IDs identify fixed instrument geometry and modes. A mode or
geometry change receives a distinct ID. The contract does not add a generic
nested configuration tree. A named survey strategy references one instrument
mode. Registry loading must reject ID collisions and invalid relationships
rather than silently selecting one mode.

### PA policy

The v3 PA policy uses exactly the frozen modes `fixed`, `per_pointing`,
`user_selected`, and `not_applicable`. The profile's one stored angle/default is
`Footprint.position_angle_deg`; policy does not duplicate it. Angles are
astronomical degrees east of north on the ICRS tangent plane. Existing Gate 5
orientation resolution remains authoritative.

- `fixed` requires a finite profile angle and rejects a conflicting row angle.
- `per_pointing` resolves an explicit pointing angle, then the profile default;
  if required and neither exists, geometry use/export fails.
- `user_selected` resolves one plan-level angle, optionally prefilled from the
  profile default; row overrides are invalid, and a required unresolved value
  fails.
- `not_applicable` accepts and exports no physical PA. It is for rotationally
  invariant geometry or an approximation that explicitly omits orientation.

Absent is not zero. Validation rejects nonfinite angles, missing required
values, and contradictory/forbidden values. Fixed and per-pointing values remain
on the instrument profile and individual pointing respectively; a pointing angle
must not be persisted as an instrument-wide fixed value.

### Exposure sequence

A selected strategy may persist an ordered exposure sequence. Each entry has a
stable 1-based order, finite local east and north offsets in arcseconds, and a
finite relative rotation in degrees. Order and identity are meaningful and
preserved during serialization. Offsets are transformed in the local tangent
plane independently of camera PA and lattice basis. Relative rotation affects
exposure footprint orientation only and composes with the resolved pointing PA
through the Gate 5 resolver. If PA is absent, a nonzero relative rotation modulo
360 degrees is invalid. No sequence retains Gate 5 single-exposure behavior at
the pointing center with no relative rotation.

Sequence persistence is distinct from pointing center, lattice, and detector
geometry. The format does not add visits, duration, S/N, weather, scheduling,
facility commands, or exposure-time optimization. A serialized sequence must
preserve the derived Gate 5 exposure geometry.

### Placement provenance boundary

The frozen placement-origin values are `manual`, `imported_unverified`,
`authoritative_import`, `declared_profile_lattice`, and `local_inference`.
`authoritative_import` carries the user-declared source reference. This is a
per-pointing runtime/session/catalogue fact, not instrument geometry. The profile
contract may persist profile-level placement policy where defined; it does not
put ephemeral planner events into an instrument profile. Do not duplicate a
persisted v2 lattice basis/origin in each pointing. Existing `GenerationMethod`
and `InferenceRole` retain their separate meanings and cannot promote an
unverified import to authoritative.

## Migration and serialization

Importing v2 into v0.4 is a lossless read, not an automatic migration. A
structural lift may copy geometry or policy fields whose meaning is unchanged.
It must not invent fidelity, role, provenance, PA policy, sequence, or
authoritative placement origin. Where v2 lacks a value required by v3, an
explicit semantic migration requires supplied scientific information and the
confirmation required by the contract; there is no automatic “upgrade all” path.

V3 serialization emits only declared fields, retains meaningful sequence order,
and does not emit fabricated optional semantics. Round trips preserve validated
meaning. V2 serialization remains on the existing path. In particular, the
canonical S-PLUS v2 document keeps its member names, values, field set, and
deterministic sorted-key serialization; generated S-PLUS output remains
byte-compatible. Arbitrary input whitespace or input key order is not promised
to survive serialization.

## Compatibility and validation evidence

Compatibility acceptance is defined by the unchanged strict v2 validators and
the frozen regression suites for T80/S-PLUS, corrected registered
`legacy_splus`, inline-v1 behavior, existing v2 imports, Gate 4 lattice, Gate 5
PA/sequence runtime, and catalogue workflows. V2 remains legacy semantics and
is never upgraded by inferred metadata. A v0.3 reader continues to accept pure
v2 output and reject v3 members; a v0.4 serializer never removes v3 fields to
make a document appear v2.

The clean starting baseline passed 101 focused tests. The focused v3
schema/document/migration set passed 39 tests across three files. Final
`make test` passed all 595 tests in 40 files. `make lint`, `make typecheck`,
`make build`, and `git diff --check` passed. The build retained Vite's existing
large-chunk advisory.

V3 regression evidence covers explicit version dispatch, instrument-only
import/register/retrieve/export/reimport, survey references, strict unknown
fields, frozen fidelity/role/PA values, explicit migration, and unchanged Gate
5 derived exposure geometry after sequence round trip. Full regressions include
the corrected S-PLUS contract, inline-v1 behavior, v2 imports, Gate 4 lattice,
Gate 5 PA/sequences, and catalogue workflows. No final instrument library,
Gate 6B behavior, or Gate 7 authoring workflow was added.

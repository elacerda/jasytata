# Jasytata v0.5.0 Gate 7: workflow and reproducibility validation

Date: 2026-10-01

Branch: `0.5.0`
Scope: integrated project workflow and versioned project recipe. This gate does not alter planner algorithms, thresholds, coverage semantics, CSV products, or the frozen v0.4.0 scientific baseline.

## Manifest contract

The browser exports `jasytata-project.json` using format `jasytata-project`, schema version `1`, and the current `frontend/package.json` version as `app_version` (currently `0.4.0`). JSON keys are sorted recursively and output is pretty-printed with a final newline. Numeric scientific values are finite decimal degrees unless the field name explicitly supplies another unit; lattice basis vectors are local east/north degrees, fixed origins are ICRS degrees, and instrument/sequence PA inputs are degrees east of north.

The authoritative recipe fields are:

- Exact instrument and optional observing-strategy registry IDs.
- Planning mode (`manual_pointings` or `regional_mosaic`), selected ICRS polygon, and user-declared project placement policy.
- Placement authoring mode and parameters, independent or follow-instrument-PA relationship, origin mode and fixed-anchor coordinates where selected, plus the resolved canonical basis in degrees. Import recomputes the basis and checks it against the declared authoring, PA, and origin before applying the project.
- Registered instrument PA policy and requirement, user PA input when applicable, `Complete` or `Efficient`, and the optional registered sequence coverage-basis selection.
- External catalogue dependency descriptors and only the custom profile documents needed by exact project or catalogue-instrument references. Bundled instrument and strategy profiles remain stable ID references.

## Authoritative and derived state

The manifest is a recipe, not a pointing export. It excludes candidate previews, candidate and coverage masks, metrics, proposal and accepted-pointing caches, sequence-expanded caches, Worker state, progress, map viewport, and layer visibility. Import clears pending and accepted proposals, coverage/readout state, previews, reference marker, debug request state, and selection state. A new plan must be generated from the restored inputs. Nominal and expanded CSV contracts remain separate and unchanged.

Project placement remains project-owned with `user_declared` provenance. It is never copied into an instrument or survey profile. Observing strategies are referenced by their registered IDs and their sequence is reused from the resolved profile; the manifest does not author or duplicate that sequence.

## Profile references and catalogue policy

The active instrument and observing strategy are resolved independently from the current registry and their association is checked exactly. For an imported custom profile, the selected registered definition is embedded as a profile dependency. If a custom active or catalogue-source profile is registered but its source document is unavailable for embedding, export fails with an actionable error. Import validates profile dependencies in an isolated registry copy, checks compatibility, and only installs custom definitions after the complete recipe and external-input checks succeed.

Loaded catalogue rows affect coverage and, depending on the selected planning path, inference. They are external project inputs: the manifest stores no rows and no machine-specific path. Each dependency records its basename, row count, coordinate columns, assigned instrument, inference role, and SHA-256 over normalized planner-relevant rows. The normalized digest includes coordinates, declared PA, source/enable state, profile and strategy assignment, inference role, and canonical grouping partitions; random session IDs, map styling, display labels, raw CSV spelling, and unrelated row metadata are excluded.

Import matches dependencies one-to-one by the declared descriptor and normalized SHA-256. Extra unmatched catalogues do not affect an imported recipe. If a declared catalogue is absent, import succeeds with an explicit incomplete-project status and planning/export stay disabled until the exact dependency is supplied. Projects with no catalogue dependencies remain complete and can plan from their selected instrument, region, and project placement alone.

## Transaction and run fencing

Import reads the file, parses JSON, validates the complete schema and region/placement/PA, resolves exact profile references, checks custom profile dependencies, and matches available catalogues before changing current project state. Parse, validation, reference, or stale-import failures leave project inputs and planning outputs untouched. A valid import with a missing external catalogue is applied as an explicitly incomplete project.

After a successful import, the active Worker is aborted, the project revision advances, and all derived outputs from the previous project are cleared. The same revision and run-identity fencing protects New project. Import captures the revision before asynchronous file reading and catalogue matching, so an import that finishes after New project cannot overwrite that reset.

## Empty-project workflow

The standalone workflow was exercised without an initial catalogue:

`New project → select MUSE instrument → set region → Regional mosaic → apply rectangular placement → Generate plan → review proposal`

The Generate action produced nominal pointings from the selected instrument and project placement while the catalogue remained empty. Catalogue loading stays available for extending existing projects.

## Round-trip and planning evidence

Focused manifest and App tests currently pass: 12 contract tests and 9 workflow tests (21 total). They cover deterministic JSON; rectangular, triangular, and advanced-basis placements; fixed-anchor and region-center origins; independent and follow-instrument-PA rotation; Complete and Efficient; selected and absent strategy; polygon/rectangle geometry, RA wrap, and high declination; an empty-catalogue project; custom profile references; external catalogue matching; malformed/future/incomplete manifests; transactional rejection of every invalid-manifest category; successful import invalidation; New project reset; and old Worker/import completion fencing.

For the same canonical project inputs, the original and manifest-round-tripped project produce exactly equal candidate order, selected nominal pointings and coordinates, coverage metrics, selection stop reason, and—when the registered SAMI strategy applies—ordered exposure expansion. Equality is exact because both executions use the same deterministic planner and canonical degrees; no scientific tolerance or expected fixture was changed.

## Limitations and pending browser checks

Catalogue contents remain external and must be supplied again on another session or machine. A changed file, row order, coordinate, PA, profile assignment, inference role, or grouping partition will not satisfy the original dependency fingerprint. The user must resolve the exact dependency or start a new project recipe. SHA-256 catalogue matching requires browser Web Crypto.

No real browser surface was available in this environment. File chooser behavior, actual download behavior, and the complete workflow still need real-browser validation in Gate 8. The App tests use jsdom and establish state and action wiring only; they are not browser-level evidence. Gates 2–6 browser checks remain pending as previously recorded.
